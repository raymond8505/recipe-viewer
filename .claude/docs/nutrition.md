# Nutrition — Ingredient Manager, Catalog, and Resolution

A recipe's ingredients are `recipe_ingredients` rows (`RecipeIngredient` entities, grouped as `RecipeIngredientGroup[]` — see [recipe-schema.md](recipe-schema.md)); each row optionally links to a canonical `ingredients` catalog row (per-100g nutrition + `density_g_per_ml` for volume↔weight conversion, USDA FoodData Central-sourced).

**Ownership invariant:** `recipe_ingredients.raw_text` **is** the recipe's ingredient text. Normalization never rewrites it — it only fills in `ingredient_id` / `match_status` / `confidence` / `estimated_grams`. Nothing may feed catalog data back into the line text.

## Catalog and matching

**`ingredients.embedding` is NOT NULL** (migration 0006): `CreateIngredientInput.embedding` is required and `UpdateIngredientPatch.embedding` can replace but never clear. Rationale: an embedding-less row is invisible to matching → every line resolving to it would be misclassified as novel.

**`match_ingredients` is hybrid keyword + semantic** (migration 0007): pg_trgm trigram similarity over `name` + each alias (best-of), fused with pgvector cosine via Reciprocal Rank Fusion (`rrf_k=50`, per-signal weights, all defaulted in SQL). Returns `semantic_similarity`, `keyword_similarity`, `score`. **Never threshold on `score`** — RRF is rank-only; threshold on the raw similarities (keyword ~1.0 = near-exact name/alias hit). Trigram was chosen over tsvector deliberately: ingredient names are 1–4 words where `ts_rank_cd` is meaningless and stemmed FTS misses typos. The single scored-CTE seq scan is intentional at catalog scale; the Supabase docs' two-limited-CTE + trgm/hnsw-index shape is the upgrade path if the catalog grows large.

## Line identity, data layer, normalization

**Line identity is the `recipe_ingredients` row's own primary key — never text or position.** `RecipeIngredient.id` IS the row (`db/migrations/0016`); `recipes.ingredients` points straight at it. Line text and array position are *display data* — people fix typos, reword and reorder, and none of that changes which food the line means. So:
- **An existing association is never re-guessed.** Normalization fills gaps only — a row that already has an `ingredient_id` keeps it, whatever the matcher thinks this run. The user changes an association through the UI; nothing else may.
- **Rewording, reordering and regrouping do not schedule normalization.** `reconcileRecipeIngredients` (`src/lib/recipeIngredientReconcile.ts`) reports `lineSetChanged` only when a line genuinely appeared or disappeared. A reword produces an `updates` entry instead: a deterministic re-parse of `raw_text`/`quantity`/`unit`/`name_text` with no model, no catalog read, and no association change. It drops `estimated_grams` only when `quantity`/`unit` actually moved (a stored weight overrides the density-derived value, so a stale one would silently win).
- **A line with no usable id claims an unclaimed row with identical text, else it is a new line.** The text fallback exists for writers that carry no ids — a re-scrape, an MCP `create_recipe`, an agent posting bare strings — because without it a re-scrape with unchanged text recreates every row and drops every curated match. Each row is claimed once, and a line naming its id wins over a text match.
- **Every line is a row from the moment it is saved**, so there is no "never normalized" state to render: a line the matcher has not seen is simply unmatched. Normalization writes rows back by id (`updateRecipeIngredientRows`, upsert on the primary key) and never creates or prunes — the reconcile owns the row set.
- The dead columns `line_id` and `position` stay in the table and off the types; nothing reads or writes them. `scripts/sync-ingredient-columns.ts` reads `line_id` once, to bring a blob-edited recipe's rows up to its blob.

**Data layer:**
- DDL records: `db/migrations/0002`–`0005` (numbering continues the better-auth branch's `0001`), `0016`–`0018` — applied out-of-band via Supabase MCP `apply_migration`; the files are review records, there is no runner.
- `ingredients` / `recipe_ingredients` are **RLS-locked with no policies** (service-role-only, like `users`). All access goes through `src/lib/ingredients.ts` on `getSupabaseAdminClient()` — the anon client sees nothing. `ingredients.embedding` is write-only (queried via the `match_ingredients` RPC; similarity = 1 − cosine distance).
- `IngredientRepoError` kinds worth respecting: `conflict` = lower(name) unique-index collision (re-match, don't duplicate); `match_failed` = the RPC broke — **never** treat it as "no matches" (that would classify every line as novel and mint duplicate catalog rows).

**Normalization workflow** (`src/lib/normalization/graph.ts`, LangGraph; nodes are plain async fns over the raw-fetch Gemini/USDA clients — no LangChain model wrappers):
- parse (Flash-Lite structured output; deterministic `parseIngredient` fallback) → embed+match (pgvector top-5; `SIM_AUTO_ACCEPT`/`SIM_NOVEL_FLOOR` exported constants — tune there, nowhere else) → adjudicate ambiguous (Flash-Lite; no verdict → unmatched, never a guessed match) → fetch novel from USDA (catalog name = the PARSED name; USDA description kept as an alias) → persist.
- Failure asymmetry: Gemini fails → degrade; USDA fails → line unmatched but the run completes; `match_failed` → run fails **without persisting**.
- Trigger: `scheduleNormalization` via Next `after()` from `createRecipeRow`/`updateRecipeRow` — only when the reconcile reports `lineSetChanged`. The graph module loads via dynamic import inside the callback: route modules must not pull `@langchain/langgraph` statically (the auth-gate test cold-loads every route graph) — this is also why the deterministic parser lives in `normalization/parseLine.ts` rather than `graph.ts`. Two rapid saves still resolve deterministically: persist aborts if the recipe's ingredient-text fingerprint (`ingredientFingerprint(ingredientTexts(recipe.ingredients))`, `src/lib/normalization/fingerprint.ts`) moved mid-run.
- Recovery: `POST /api/recipes/[id]/normalize` (session-or-recipe-token) re-runs for the current lines; `yarn backfill:normalization [--limit=N]` processes every recipe whose stored fingerprint differs from its current lines (resumable — completed rows self-skip via the fingerprint).

**USDA client** (`src/lib/usda.ts`): the detail fetch uses `format=abridged` — **load-bearing**: the default full format 404s every Foundation record (upstream USDA regression since 2026-07, reproduced with USDA's own DEMO_KEY sample; don't "fix" it back to full). Abridged nutrients are FLAT, keyed by legacy NDB `number` (a string — sugars is 269 on SR Legacy but 269.3 on Foundation; kJ energy sits under 268 and must never win over 208 kcal) and carry NO `foodPortions`, so `food_portions` persists as null and `density_g_per_ml` falls back to a best-effort Gemini estimate (`estimateDensity`, sibling of `estimateLineGrams`; plausibility-capped, null when it declines). `fdc_id` stays on rows, so a re-import can backfill real portions if full format returns. `deriveDensity` (median g/ml over volume portions; SR Legacy hides portion units in `modifier` with `measureUnit` "undetermined") is retained for portion-bearing data. Real abridged payload fixtures in `src/fixtures/usda.ts` lock the shapes in. Search data types pinned to `Foundation,SR Legacy` (per-100g analytical; Branded/FNDDS are label/serving-based). Requires `USDA_API_KEY` (free data.gov key, 1,000 req/hr — the app crashes at startup without it per the env-enforcement design).

## Nutrition resolution

**The ingredient catalog is the ONLY source of nutrition** (PR #76 review). `schema.nutrition` is still *stored* — scrapes and `create_recipe`/`update_recipe` still accept it, and `get_recipe` still reports it as part of the stored document — but nothing reads it back as nutrition. There is deliberately **no fallback**: a recipe whose lines aren't fully matched shows no nutrition at all rather than a number nobody can trace to an ingredient, and the fix is to normalize the ingredients. Don't re-add a fallback "just for recipes without ingredients"; that is the thing that was removed.

**`ScalableRecipe` is the single interface** (`src/lib/ScalableRecipe.ts`; constructed from `(schema, ingredients, state?, normalized?)`): `nutrition()` returns `ScaledNutrition | null` — the catalog values when `fullyCovered` **and** servings are known, else null. `servingSize` is the one thing that still rides along from `schema.nutrition`, and it isn't a fallback: it's free text ("1 cup"), not a nutrient, and the catalog has no slot for it. Never re-introduce per-field merging or a parallel resolver: the panel, RecipeDetail's JSON-LD (a **default-state** instance, memoized, so user scaling never leaks into serialization), MCP `get_recipe`, and the recipe cards' `recipeNutritionBadges` all resolve through `nutrition()`. The normalized input comes from `recipeNormalizedNutrition(recipe)` (`src/lib/nutritionMath.ts`) — pure, client-safe, computed straight off the hydrated entities (each line's `ingredient` is its catalog row; absent and null both mean "no data"). Each client holder of a document (RecipeDetail, CookingMode) derives it from its own `doc.ingredients`, memoized on the groups, and hands it straight to the constructor; nothing threads it as a prop and nothing gates it on document identity. That is what keeps nutrition through a save — the `/update` echo is hydrated, catalog rows and all — while a drafted line (a re-scrape under review) or a newly added one has no row, so the recipe shows no nutrition until normalization lands and the page reloads. **Internally nutrition is object-valued**: `ScaledNutrition` fields are `NutrientValue` (`{ value: number; unit: string }`, full precision; `servingSize` stays free text) — Schema.org `"value unit"` strings exist only at the wire boundaries (`schema.nutrition` in the DB/zod layer, JSON-LD, MCP output). `parseNutrientValue` (nutritionMath.ts) is the only string→value parser and `formatNutrientString` the only wire formatter (1dp, via `nutrientValuesToSchema` — used by RecipeDetail's JSON-LD and MCP `get_recipe`); `formatNutrientDisplay` (format.ts) is the display formatter (values > 1 → integer, ≤ 1 → 2dp). `parseNutrientValue`/`schemaNutritionToValues` run in no display path at all — they are purely the inbound half of the wire boundary, and their only callers are fixtures and the label tests. Never re-introduce regex parsing of nutrition strings outside `parseNutrientValue`, or build `"${value} ${unit}"` strings outside those two formatters.

**`SCHEMA_NUTRITION_MAP` bounds what can ever be displayed.** It maps the catalog's nutrient columns to Schema.org fields, and it has no `unsaturated_fat_g` (the catalog has no such column) — so `unsaturatedFatContent` is unreachable and the label's Unsaturated Fat row can never fill, however full a recipe's stored `schema.nutrition` is. calcium/iron/potassium are tracked by the catalog but have no Schema.org slot, which is why `recipeNutritionRows` returns `micros: []`. Adding any of them is a change to that map plus the label adapters, not a fallback.

**Recipe cards get their nutrition as badge elements, not as a prop the card understands.** `recipeNutritionBadges(recipe, fields?)` (`src/components/RecipeNutritionBadge.tsx`) resolves through `nutrition()` and returns one `RecipeNutritionBadge` per field the recipe carries — calories and protein by default (`DEFAULT_CARD_NUTRIENTS`) — or `[]` when the recipe resolves none, which is the common case. `RecipeGrid` calls it as the default for its `badges` prop; `RecipeCard` takes `ReactNode[]` and knows nothing about nutrition, so which badges a card shows stays a decision of whatever renders the grid. **A list row only resolves nutrition if it was read with `getRecipes({ catalog: true })`** — see [supabase-data-layer.md](supabase-data-layer.md); without it the badges are silently empty, which is the same non-answer a half-normalized recipe gives.

**NutritionPanel's summary/label toggle is a layout swap, not a second source.** The panel's `view` state (`"summary" | "label"`, session-only, defaults to `"summary"`) picks between the curated six-stat grid and the shared `NutritionFactsLabel`. Both render the *same* `nutrition()!` values on the *same* basis (`nutritionUnitLabel` + the portion stepper); the label shows every `NutrientField` the recipe carries, where the grid shows a fixed six. Never give the label its own derivation, its own basis, or whole-recipe totals.

**`/ingredients?q=` is a load-bearing deep link.** Every matched line in the NutritionDetail table renders an external-link icon to `/ingredients?q=<catalog name>` (new tab — the include-toggle lens below is session state), so a bad catalog row gets fixed in the ingredient manager's own editor instead of a second one grown here. The manager's page reads `q` into `getIngredients({ query })` **and** seeds `useIngredientsTable`'s `query` state via `IngredientsTable`'s `initialQuery` — both halves matter: filter without seeding leaves a filtered list under an empty search box, and the seed must not trigger a client re-fetch of what the server already sent. The link is gated on the *resolved* `CatalogIngredientSummary`, not on `ingredient_id`: an unresolvable id renders "(unknown ingredient)" and has no name to search with.

**NutritionDetail's include toggles are a local what-if lens, not a nutrition source.** Every line and every ingredient group on `/recipes/[id]/ingredients` carries a checkbox; unchecking one drops it from that table's "Recipe total" / "Per portion" rows so a user can ask "what are the macros if I skip the pasta?". State is a `Set<string>` of row ids in `useNutritionDetail` — **session-only by design**, and it must stay inside that hook. Do not thread it into `ScalableRecipe`, `normalizedNutrition`, the JSON-LD, or MCP output: a partial recipe is not the recipe, and it would fight `nutrition()`'s all-or-nothing `fullyCovered` gate. The `excludedCount` warning is scoped to *enabled* lines — it flags contributions silently missing from the tally, and a deliberately switched-off line isn't silent. The hook's state is the recipe's groups themselves; the inline text edit PATCHes `/api/recipes/[id]/ingredients` by row id and swaps in the groups the server returns, and an association, estimate or grams change replaces one entity by id.

**A per-line `estimated_grams` of 0 means "don't count this line" — and it is the one exclusion mechanism that IS persisted.** Some ingredients can't reasonably be weighed ("salt to taste", "oil for frying"); they parse quantity-less, and `fullyCovered`'s zero-exclusions gate means one of them holds the *whole* recipe off its ingredient-derived total. Zero is both the signal and the mechanism: `computeLineNutrition` ranks a stored estimate first on `!= null` (never a falsy check — do not "tidy" that), so the line computes as `ok` at 0 g and `scaleNutritionToGrams` contributes nothing. Deliberately unlike NutritionDetail's include toggles, this one is *supposed* to travel: it satisfies `fullyCovered`, so it reaches the JSON-LD and MCP output. That is the point — a curator saying "this line is nothing" is a fact about the recipe, where a what-if toggle is a question about it. The grams field (`recipeIngredientGramsPatchSchema` is `.nonnegative()`; negatives 400) renders only on **matched** lines and `unmatched` is still checked first, so 0 can't rescue an unmatched line — unmatched is *unknown*, a real threat to an accurate total worth flagging, not a decision. `NutritionGramsCell` marks a 0 "not counted" rather than "est.": both are stored estimates, but 0 is a decision about the line, not a guess at its weight.
