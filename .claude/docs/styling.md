# Styling Layer — Keep It Centralized

The styling layer has **single sources of truth**. Do not re-declare style decisions at call sites — thread them back to these homes so the site and Storybook (and every component) stay in sync.

**Theme colors → `src/app/globals.css`.** Color decisions live as CSS tokens: values in `:root`, util mappings in the `@theme inline` block. The palette is **warm neutral** (June 2026 redesign): a plain `@theme` block remaps the whole `--color-gray-*` scale to stone oklch literals — so raw `gray-*` utilities render warm — and the surface tokens are warm literals (`--card`/`--popover` warm paper, `--background` stone-50). Brand stays `--brand: var(--color-orange-600)`.
- **Gray-remap gotcha:** the remap must stay in a plain `@theme` block with **literal** oklch values. Moving it into `@theme inline` (or referencing `var(--color-stone-*)`) breaks it silently — inline vars aren't emitted at `:root`, and unused palette vars are tree-shaken, which would strand the border-color compat layer and any `var(--color-*)` reference.
- In UI components use **theme-token utilities** (`bg-card`, `text-card-foreground`, `text-muted-foreground`, `border-border`, `bg-muted`, `text-brand`, `bg-brand-subtle`) — **not** raw palette utilities (`bg-white`, `text-gray-900`, `text-orange-600`).
- A new semantic/brand color is a **new token** (add to `:root` + `@theme inline`), never a hardcoded hex/gray sprinkled across components.
- Exception: genuinely one-off *semantic status* colors with no theme meaning (e.g. the green/amber/gray status pill) may stay as explicit classes, but only inside their own named component.

**Global "chrome" (fonts + page surface) → `src/components/AppChrome.tsx`.** The `next/font` loaders are called **once** here: `bodyFont = Figtree(...)` on `--font-sans` and `headingFont = Source_Serif_4(...)` on `--font-heading` (with `axes: ["opsz"]`), alongside `APP_SURFACE_CLASS` (`bg-background`), `APP_SHELL_CLASS`, and the `AppChrome` wrapper. This is the only place that decides the app fonts and page surface. The real site (`src/app/layout.tsx`) puts both `.variable`s on `<html>` and `bodyFont.className` on `<body>`; Storybook (`.storybook/preview.tsx` global decorator) wraps every story in `<AppChrome>`. Both consume the same source, so stories render with the same chrome as production. Never call a font loader or set the background/font on an individual page/story — change `AppChrome`.
**The app is a shell: `<body>` is `h-dvh` and `<main>` is the scrollport.** `APP_SHELL_CLASS` gives the body the site's one definite height, and `<main>` (`flex min-h-0 flex-1 flex-col overflow-auto`) is the only element beneath it with a height to inherit from. **A screen that should fill the viewport says `flex min-h-0 flex-1 flex-col` on its root and hands the same classes down to whatever must grow** — `/recipes/[id]/ingredients` and `/ingredients` are the worked examples, each ending in a scroll box that is `flex-1 min-h-0` (with `max-h-[100dvh]` as its cap when a story or a test renders it with no such parent). Never size a screen by subtracting the chrome (`calc(100dvh - 7.5rem)` and friends): the arithmetic silently misses things — the header's `border-b` was worth a whole pixel of page scrollbar — and it goes stale the moment the chrome moves.
- **Do not wrap `{children}` in a centring div.** `<main>` centres the page itself (`items-center` + `[&>*]:w-full [&>*]:max-w-6xl`) because an intermediate wrapper would be auto-height, and an indefinite ancestor stops every height below it from resolving — `flex-1` children of such a box fall back to their content size. Keeping `<main>` full-width also puts its scrollbar at the window edge rather than inset at the column's.
- An ordinary page needs none of this: its content flows in `<main>` and scrolls there, bottom padding included.
- **A dropdown inside a scrollport measures its side — `src/lib/dropdownPlacement.ts` + `useDropdownPlacement`.** A hard `absolute top-full` panel opens *under* whatever is pinned at the scrollport's bottom edge (`NutritionDetail`'s totals band), and a scroll box's own `overflow-auto` clips it there, so the options on the last rows are unreachable at any z-index. The helper measures the room between the trigger and the scrollport's edges **minus the sticky `thead`/`tfoot` inside it**, then picks `bottom-full mb-1` over `top-full mt-1` and caps the panel to the room it actually has. It flips only when below genuinely can't hold it *and* above is roomier — an unmeasured layout reports 0 on both sides (jsdom), and the strict comparison is what keeps that rendering as it does today. This is the repo's one dropdown-placement path; give the next overlay this hook rather than a second copy of the arithmetic.
- **An open/closed editor swap must not change its box's height.** `IngredientAutocomplete` replaces its closed trigger with a single-line `<input>`, and its host column is a hard `w-44` where a catalog name wraps to two or three lines — so the closed label stays rendered `invisible` as a sizer in a 1×1 grid with the input over it, both from one shared `label` node. `min-h-9` is only the floor for a one-line name; it cannot hold a wrapped one. jsdom does no layout, so the parity is a story (`OpenAndClosedMatchHeights`, pinned to a literal 176px because the wrapping is the point — the short fixture names never wrap) and the tests assert the sizer's presence, not heights. **`MealSearch` has both this swap and the naive `top-full`, and neither fix** — it is the obvious next caller for both.
- **`tall:` is the height breakpoint** (`@custom-variant tall (@media (min-height: 500px))`, globals.css). Tailwind's own breakpoints are width-only, and a screen that fills the viewport rations vertical space — `NutritionDetail`'s pinned totals band is `tall:sticky`, giving a short screen those rows back. Reach for it whenever chrome earns its keep only on a tall viewport, rather than inventing a second height query at the call site.
- Top-level loader calls in this shared module are statically analyzable, so both Next's `next/font` transform and Storybook's vite plugin pick them up — verified with `next build` + `build-storybook`. (An earlier note claimed the loader had to be duplicated per compiled entry; that was overcautious — it does **not**.)
- **Typography language (June 2026 redesign):** headings are serif-light — a base-layer rule puts `font-heading font-light` on `h1`–`h6`; body defaults to `font-light` Figtree. Eyebrow labels (uppercase + tracking-widest section headers) opt back into `font-sans font-semibold`. Non-h-tag elements that mirror headings (`RecipeTitleInput`, the header logo) carry explicit `font-heading` classes. Don't reintroduce `font-bold` on headings — hierarchy comes from size.

**Purpose-built badges/pills → named components wrapping a shadcn primitive.** Never inline a styled `<Badge>` or a hand-rolled `<span>` pill in a feature component. Each badge variant is its own named component that wraps `@/components/ui/badge` and owns its styling + logic — e.g. `RecipeStatusBadge` (status normalization + status colors), `RecipeCategoryBadge` (brand accent), `RecipeNutritionBadge` (neutral surface + the per-nutrient label map).

**A recipe card has two badge slots and derives neither.** `RecipeCard` takes `topBadges` (overlaid on the image, top right) and `badges` (in the footer, after the time), both `ReactNode[]`, and renders whatever it is handed. What goes in them is a decision about the *listing*: `RecipeGrid` fills the top slot with the recipe's first category and its status (the latter only when `showStatusBadge` is set), and the footer with `recipeNutritionBadges`. A caller's own `topBadges`/`badges` function replaces those defaults outright. Keep the brand accent to one badge per card — the category wears it, the rest are neutral, so the accent keeps meaning something.

**A supplier of `topBadges` prepends to `defaultTopBadges`, it does not rebuild it.** `defaultTopBadges` (exported from `RecipeGrid`) owns the category/status pair and the status-last rule; a listing adding a badge of its own spreads its badges in front of it. The home page is the worked example: with a search query it prepends `recipeMatchBadges`, so the row reads match → category → status. `RecipeMatchBadge` is `bg-green-100 text-green-700` — an explicit color class, not a token, on the same grounds `RecipeStatusBadge` states for its per-status colors: it marks a search hit, not a surface. **It shares that exact green with the `published` status badge**, so on a published card the row's first and last pills match; if that ever needs separating, change the match badge, since status colors are load-bearing across the app.

**The status badge is always the LAST top badge.** The overlay is `justify-end`, so badges pack towards the corner and the last one is the one in it — which is where a reader looks for "is this published?". Everything else grows leftwards from it. Any function supplying `topBadges` owes the status that slot.

The overlay sits **after** the image in DOM order, which is what paints it on top — it carries no `z-index`, and does not need one. This mirrors the icon-component rule in [CLAUDE.md](../CLAUDE.md)'s repo-wide conventions. The shadcn primitive's base already supplies padding/size/weight — the wrapper sets only what differs.

**shadcn primitives → `src/components/ui/`** (generated; treat as unedited). Feature components compose them; overrides go through `className` (twMerge last-wins), not by editing the generated primitive.
- **Deliberate divergence from the registry (June 2026 redesign):** `button.tsx` and `badge.tsx` carry `rounded-full` in their cva bases (site-wide pill shape for interactive elements), `button.tsx` also carries `cursor-pointer` (see the cursor rule below), and `input.tsx`/`textarea.tsx` are underline fields (`rounded-none border-0 border-b`, no focus ring — focus is `focus-visible:border-brand`). These are the sanctioned kind of primitive edit (global shape re-themes tokens can't express). If any of these files is ever regenerated from the registry, re-apply the divergence. Raw `<input>`/`<select>` elements in feature files follow the same underline pattern with `focus:border-orange-400`.
- **`data-*` variants in registry files are shadcn's, not Radix's.** `globals.css` line 5 does `@import "shadcn/tailwind.css"`, which declares `@custom-variant data-open/closed/checked/unchecked/selected/disabled/active/horizontal/vertical`. Each matches **both** the Radix attribute and the bare one — e.g. `data-checked:` compiles to `:where([data-state="checked"]), :where([data-checked]:not([data-checked="false"]))`. So `data-checked:bg-primary` in a generated file works as shipped; do **not** "fix" it to `data-[state=checked]:`. There is no `data-indeterminate` variant, so tri-state controls (see `checkbox.tsx`) need the arbitrary `data-[state=indeterminate]:` form. If you ever suspect a variant isn't compiling, grep the built CSS for the **escaped class name** (`data-checked\\:`) — Tailwind escapes brackets in class names and emits selectors unquoted, so searching for `data-[state` or `data-state="checked"` returns nothing either way and proves nothing.
- **Cursor doctrine: never add `cursor-pointer` at a call site.** Tailwind v4's preflight dropped v3's `button, [role="button"] { cursor: pointer }`, so every control renders with the UA default arrow. A base-layer rule in `globals.css` restores it for `button`, `select` and `[role="button"]` (disabled ones excluded — they get the plain arrow, not `not-allowed`). If a button shows the wrong cursor, that rule is the thing to change. The `cursor-pointer` in `button.tsx`'s cva is **not** redundant with it and must stay: `<Button asChild>` renders whatever it wraps, and `NutritionPanel` wraps a `<Link>`, so that one is an `<a>` the element selector never matches — the two rules cover different sets (element vs appearance). A deliberate override still works from a call site because `@layer utilities` outranks `@layer base` regardless of specificity — `DragHandleButton`'s `cursor-grab active:cursor-grabbing` is the worked example, and is the thing to re-check if the base rule is ever widened. A `<label>` is outside the rule's scope, so the row-covering label in `IngredientListItem` keeps an inline `cursor-pointer`.
- **Radius doctrine:** the `--radius-sm..4xl` scale in `globals.css` is **flattened** — every `rounded-sm..4xl` utility renders `var(--radius)` (2px). Surfaces are near-square; only `rounded-full` escapes. Don't "fix" a call site by swapping `rounded-lg` for `rounded-xl` — they're identical; change `--radius` if the tightness is wrong. Arbitrary radii (`rounded-[4px]`) bypass the flattening — registry files that ship one get it rewritten to `rounded-sm`.
- These are the **`radix-nova`** style (per `components.json`), not vanilla shadcn — quirks worth knowing when matching a hand-rolled look: `Card` uses `ring-1 ring-foreground/10` (not `border`) + a `--card-spacing` var for padding/gap; `CardTitle` is a plain `<div>` with **no `asChild`**.
